# レビュー工程サポート 設計書

- 日付: 2026-08-16
- ブランチ: experiment/ui-scaling
- ステータス: 承認済み（ユーザー合意ベースで作成）

## 背景・目的

各工程（UI/PG/PT/IT/ST）には、工程の締めとしてレビューが入ることがある（各工程に0回か1回）。
現状のデータモデルにはレビューの概念がなく、レビュー工数は親工程に混ぜて入力するしかない。

本機能の目的:

1. **工数の区別**: レビューの見積・実績を親工程と区別して記録し、レポートで内訳として見られるようにする
2. **スケジュール管理**: レビューの実施タイミング（各工程の終盤〜直後）をスケジュール・ガント上で管理できるようにする

## 決定事項（ユーザー合意）

| 論点 | 決定 |
|------|------|
| レビューの粒度 | 各工程に 0回 か 1回 |
| 集計モデル | **親工程の内訳**方式。集計の基本は従来通り5工程で、レビューは「うち何h」の内訳として扱う |
| データモデル | **レビュー行方式**（案A）。isReview フラグ付きのレコード行として見積・実績・スケジュールを統一拡張 |
| Excel取り込み | 今回は対象外。ただし将来「レビュー列→isReview行」で自然に拡張できる構造にする |
| 実装順序 | Phase 1（データ＋見積入力＋レポート内訳）→ Phase 2（実績）→ Phase 3（スケジュール） |

### 検討して不採用にした案

- **独立工程方式**（UIレビュー等を PROCESS.TYPES に追加）: 工程リストが約20ファイル・245箇所に波及しており、列倍増による画面の横膨張も大きい。レビューが「親工程に従属する0/1のサブステップ」であるドメイン実態とも合わない。
- **付帯フィールド方式**（見積行に reviewHours を追加）: レビュアーが別担当者（上長等）の場合を表現できず、実績の日単位記録・スケジュールの独立期間化もできないため要件を満たさない。

## データモデル

見積（estimates）・実績（actuals）・スケジュール（schedules）の各レコードに、
省略可能なブールフィールド `isReview` を追加する。

```js
// 本作業行（従来のまま・変更なし）
{ id, version, task, process: 'PG', member: '森', hours: 10, workMonths, monthlyHours }
// レビュー行（新規）
{ id, version, task, process: 'PG', member: '佐藤', hours: 2, isReview: true, workMonths, monthlyHours }
```

- **省略時は false 扱い**（既存データの移行処理は不要）
- レビューは概念上、工程ごとに1つのサブステップだが、レビュー会に複数人が参加するケースを
  許容するため、**レビュー行にも複数担当者（複数行）を許す**（既存の複数担当者機構と同じ）
- 工程別合計は「(version, task, process) の全行合算」であり、既存集計コードは無変更で
  レビュー分を含んだ正しい合計を返す。内訳は `rows.filter(r => r.isReview)` で導出する

### レコード同一性キーへの影響（重要）

現状、複数箇所でレコードの対応付けに `(version, task, process, member)` を使っている。
レビュー行は本作業行と同キーになり得るため、以下では **isReview をキーに追加**する:

- **merge-core / merge-json**: 差分マージのレコード同一性判定。忘れると本作業行とレビュー行が
  同一視されてマージで潰れる
- **スケジュール自動生成の既存スケジュール判定**（generateSchedulesFromEstimates 内）:
  本作業スケジュールの存在だけでレビュー分の生成がスキップされる誤判定を防ぐ

以下は対応不要（自動で正しく動く）:

- **履歴（Undo）**: レコード全体のスナップショット方式のため
- **JSONバックアップ／エクスポート／インポート**: フィールドがそのまま保存されるため
- **normalizeEstimate**: isReview を透過するため
- **編集モーダルの行対応付け**: estimateId ベースのため

## Phase 1: 見積入力＋レポート内訳

### 全工程一括モーダル（estimate-add.js / index.html）

- 各工程行の既存「＋担当者」ボタンと並びで「＋レビュー」ボタンを追加
- 押すと通常行と同型の行（担当者・工数・作業月）が **「R」バッジ付き**で追加される
  （`data-review="true"` を行に付与し、保存時に `isReview: true` を立てる）
- 編集時のプリフィル: isReview 行はレビュー行として展開（estimateId 対応付けは既存機構を流用）
- バリデーション: レビュー行も担当者・工数必須（通常行と同一ルール）

### 見積一覧（マトリクス表示、estimate.js）

- レビュー行はセル内で「R」バッジ付き表示
- セルの工数合計は従来通り全行合算（変更なし）

### レポート（report.js）

- **工程別見積vs実績バーチャート**: 各工程バーの上部にレビュー分を明度違いのセグメントで積み、
  ラベルに「うちR: xh」を併記。バー総高さ＝工程合計は従来と同じ
- 円グラフ・工程別精度など他の集計は**変更なし**（全行合算のままで正しいため）
- 内訳表示は Phase 1 ではこの1箇所に絞る（YAGNI。レビュー合計カード等は必要になったら追加）

### Phase 1 対象外

- クイック見積入力（quick.js）: 通常モーダルで入力可能なため対象外。要望が出たら追加

## Phase 2: 実績入力

- **実績追加フォーム**（actual.js）: 工程選択の横に「レビュー」チェックボックスを追加。
  ON で `isReview: true` の実績として登録
- **実績一覧・日別表示**: レビュー実績に「R」バッジ表示
- **タイムライン（actual-timeline.js）**: レビュー実績の区別表示（縞・バッジ）のみ。
  D&D での新規作成は通常フォーム経由とし、必要になったら拡張

## Phase 3: スケジュール

### 自動生成（schedule.js: generateSchedulesFromEstimates）

レビュー見積行からも独立スケジュールを生成する。配置ルール:

1. 同一タスク内の処理順を「工程順 → 本作業 → レビュー」とする
2. レビュー行の開始日 = max(同一工程の本作業の終了日の翌営業日, 担当者の空き日)
3. レビュー終了日を `task::process` の終了日マップに反映し、
   **次工程はレビュー完了を待って開始**する（レビュー通過で次工程へ、という実態と一致）

### 表示・入力

- **ガント表示**（schedule-render.js）: レビューは親工程色のストライプ柄バー＋ラベル「PG R」等で区別
- **手動追加フォーム**: スケジュール追加モーダルにレビューチェックを追加

## エラー処理

- 新しい失敗モードはほぼない。旧データ（isReview 無し）は一律 false 扱いに統一する
- レビュー行のバリデーションは通常行と同一（担当者・工数必須）

## 検証

- 各 Phase 完了時に `/verify-ui`（Playwright 実ブラウザ・DOM 機械判定）で検証し、
  PASS するまで完了報告しない
  - Phase 1: レビュー行の入力→保存→一覧の R バッジ表示→レポート内訳セグメント描画
  - Phase 2: レビュー実績の登録→一覧・日別表示
  - Phase 3: 自動生成でレビューが本作業後に配置され次工程が待つこと→ガントの区別表示
- seed データにレビュー行を含めたケースを追加する
- 各 Phase 検証 PASS 後に `/deploy` 実行
