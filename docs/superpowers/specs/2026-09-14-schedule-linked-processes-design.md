# スケジュール機能: 工程間「連結ペア」ドラッグ機構 設計書

- 日付: 2026-09-14
- ブランチ: `experiment/ui-scaling`（実装は `feature/<topic>` 隔離worktreeで行う）
- 関連: `docs/GANTT_CHART_SPEC.md`, `docs/GANTT_CHART_DESIGN.md`, `mockups/schedule-redesign/`

## 背景・目的

スケジュール（ガントチャート）機能で、同一担当者の同一対応（タスク）内において、
特定の工程ペア（IT→ST、PG→PT）が隙間なく隣接している場合、これを一続きの作業として
扱いたい。

- 前工程（IT/PG）をドラッグして移動すると、隣接する後工程（ST/PT）も連動して追従し、
  隙間ゼロの状態を維持したまま移動する。
- 後工程（ST/PT）を単独でドラッグした場合は、後工程だけが移動する（前工程には影響しない）。

現状、IT/ST・PG/PT はそれぞれ独立した`schedule`レコード（`version`+`task`+`member`+`process`の
組み合わせで1レコード）として存在し、工程間の連結・依存関係を保持する仕組みは存在しない
（`js/schedule.js`, `js/schedule-render.js`, `js/state.js`, `js/constants.js` 全体を確認済み。
`dependency`/`groupId`/`linkedSchedule`等のキーは一切ない）。自動生成時
（`generateSchedulesFromEstimates`）はIT→ST等の順序で隙間なく計算されるが、これは生成時
一回限りの計算であり、手動移動時には再評価されない。

## スコープ

- 対象ペア: `IT-ST` と `PG-PT` の**両方**を最初から実装する（ハードコードではなく
  「連結ペアリスト」として一般化し、将来ペアが増えても定義追加だけで対応できるようにする）。
- 対象外: `UI`→`PG`、`PT`→`IT`など、上記2ペア以外の工程間の連結は行わない
  （チェーン化はしない。各ペアは独立）。
- 対象外: 同じ担当者行での予定重なり時の重ね描き問題（`mockups/schedule-redesign/README.md`
  記載の既知課題）は本設計のスコープ外。混ぜて直さない。

## データモデル

新しいフィールドを`schedule`オブジェクトに追加しない。連結は**都度、位置関係から導出**する
（永続化されたリンクIDやフラグを持たない）。

`js/constants.js` の `PROCESS` に連結ペア定義を追加する:

```js
PROCESS.LINKED_PAIRS = [
  ['IT', 'ST'],
  ['PG', 'PT'],
]; // [前工程, 後工程]
```

### 連結判定ロジック

ある前工程スケジュール `front`（`process`が `LINKED_PAIRS` のいずれかの前工程側）について、
以下をすべて満たす `back` スケジュールが存在する場合、`front`と`back`は「連結中」とみなす:

1. `back.version === front.version`
2. `back.task === front.task`
3. `back.member === front.member`
4. `back.process` が `front.process` に対応する後工程（例: `front.process === 'IT'` なら
   `back.process === 'ST'`）
5. `back.startDate` が `front.endDate` の**翌営業日**と一致する（既存の稼働日計算ロジック
   ＝土日・祝日考慮）

隙間がある場合（4も5も一致するレコードがない場合）は連結中とみなさず、独立した2本の
スケジュールとして扱う。

この判定は前工程を掴んだ瞬間（`mousedown`/タッチ開始）に1回評価し、ドラッグ操作中は
その結果（連動対象の`back`があるかどうか、あるとすればどのレコードか）を保持する。
ドラッグ中に判定をやり直すことはしない。

## ドラッグ時の挙動

### 前工程（IT/PG）を掴んで移動する場合

- 連結中の後工程が存在する場合、ドラッグプレビュー中（マウスボタンを離す前）から後工程の
  プレビューバーも一緒に追従して表示する。
- 確定時（`mouseup`）:
  1. 前工程の新しい`startDate`/`endDate`を、既存ロジック（`calculateEndDate`等）で
     通常通り再計算する。
  2. 連結中の後工程が存在した場合、後工程の新しい`startDate`を
     「前工程の新しい`endDate`の翌営業日」として設定し、後工程の`endDate`は
     後工程自身の`estimatedHours`を使って既存の稼働日計算ロジックで再計算する。
  3. 単純な日数シフト（同じ日数だけ平行移動）ではなく、営業日ベースで隙間ゼロを
     再現する方式にする。土日・祝日をまたぐ移動でも連結（隙間ゼロ）が崩れないようにする
     ため。

### 後工程（ST/PT）を掴んで移動する場合

- 後工程だけが移動する。前工程には一切影響しない。
- 移動の結果、後工程が前工程と重なる・追い越す配置になっても**制約なし・警告なし**
  （既存の単一スケジュールドラッグと同じ挙動に揃える。現状の実装にも重なりチェックは
  存在しないため、一貫性を優先する）。

### 非対称性について

連結は「前工程を掴んだ場合のみ後工程が追従する」一方向の仕組みであり、後工程側からの
逆連動（後工程を動かすと前工程も動く）は発生しない。

## Undo/Redo

前工程と後工程が連動して同時に変化した場合も、ユーザー操作としては1回のドラッグ操作
なので、**1回のUndoで両方のレコードが元に戻る**ようにする（2回Undoしないと戻らない、
という体験を避ける）。既存の`pushAction`（`js/schedule.js:1693`付近）を1件ずつ2回呼ぶ
実装だと2回Undoが必要になってしまうため、実装計画フェーズで「複数レコードの変更を
1つのUndoアクションにまとめる」方法を検討する。

## 影響範囲（実装計画フェーズで詳細化する項目）

- `js/schedule.js`: `handleScheduleDrag`（`schedule.js:1681`付近）に、連結判定・後工程の
  シフト処理を追加する。連結判定用のヘルパー関数（前工程スケジュール→連結中の後工程を
  返す）を新設する。
- `js/schedule-render.js`: マウス版`setupDragAndDrop`（`schedule-render.js:1703`）・
  タッチ版`setupTouchHandlers`（`schedule-render.js:1974`）の両方で、ドラッグプレビュー
  描画（`drawDragPreview`）に後工程バーの追従表示を追加する。2つの実装が並行して
  存在するため、両方を漏れなく更新する。
- 稼働日（土日・祝日）を考慮した「翌営業日」計算は、既存のロジック（`calculateEndDate`
  等が内部で使用している稼働日計算）を再利用する。新規に実装しない。

## テスト方針

- 特性テスト（`tests/`、`node --test`）で以下を検証する:
  - IT-STが隙間なく隣接している状態でITをドラッグすると、STも同じ営業日数だけ
    連動して移動し、隙間ゼロが維持されること。
  - IT-STの間に隙間がある状態でITをドラッグしても、STは移動しないこと。
  - STを単独でドラッグすると、STだけが移動し、ITは変化しないこと。ITと重なる位置に
    移動しても制約されないこと。
  - PG-PTについても同様のケースを検証する（IT-STと同じロジックが再利用されていることの
    確認を兼ねる）。
  - 連動した移動が1回のUndoで両方元に戻ること。
- Playwright e2e（`tests/e2e/`）で、実際のドラッグ操作によるプレビュー追従・確定後の
  表示を確認する。

## 未決事項・非対象

- UI/PT/IT間などの追加ペアや、3工程以上のチェーン連結は今回のスコープ外。将来
  必要になった場合は`PROCESS.LINKED_PAIRS`に定義を追加するだけで拡張できる設計に
  している。
- 重なり時の重ね描き問題（既知の別課題）は本設計では扱わない。
