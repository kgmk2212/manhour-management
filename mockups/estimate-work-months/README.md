# 見積の「工程ごとの作業月」設定 UI 刷新モックアップ

BACKLOG **B-047**。見積登録／「全工程を編集」モーダル（`index.html` `#addEstimateModal`、`js/estimate-add.js`）で
工程ごとの作業月を決める UI を、現状の「開始 select 〜 終了 select」から置き換える 3 案を比べる。

## 目的

- 複数月の対応で、工程ごとに作業月を設定するのが手間。**単一月にしたい工程でも開始月・終了月の両方を触る**。
- もっと視覚的に設定したい。ただし **1 工程に複数担当者（＋レビュー行）× 複数月** の全組み合わせに効くこと。
- 既知の制約・不具合を同時に解消する: 全体期間が 2ヶ月のとき 2ヶ月に跨げない（単一 select）、スマホ 390px で月ラベルが読めない（B-046）、
  均等按分の未丸め保存（B-041①）。

## 現状の課題（`current.html` で再現）

- `updateAddEstimateTableHeader`（`js/estimate-add.js:965`）が期間 3ヶ月以上なら行ごとに 開始select〜終了select、2ヶ月なら単一 select を作る。
  追加担当者行・レビュー行（`tr.est-extra-member-row`）も `ensureExtraRowMonthCell` で同じ select を持ち、**連動は無い**（同じ月を人数分選ぶ）。
- 単一月行は a62f797 で終了月が開始月に追従するようになったが、複数月にするには依然 2 select、月は開くまで見えない。
- スマホでは列幅 100px に 2 select を押し込むため月が読めない（B-046。`current.html` のスマホ表示で再現している）。

## 確認方法

ブラウザで `index.html`（比較ハブ）を開く。実物の `../../style.css` を読み込むため、色・フォント・部品は本番と同一。
Playwright MCP は `file:` を拒否するので、リポジトリ直下で `python -m http.server 8941` などで配信し
`http://127.0.0.1:8941/mockups/estimate-work-months/index.html` を開く。

- 4 ページ（現状 / 案A / 案B / 案C）とも **同じ 8 行の見積・同じ作業期間 2026-08〜11・同じ課題** から始まる。
  課題: V2.4 帳票A出力改修、PG は田中 60h・佐藤 40h・レビュー鈴木 8h、初期値はウォーターフォール式の既定（UI=8月, PG=9月, PT・IT=10月, ST=11月）。
  1. PG の田中・佐藤を 8〜10月（3ヶ月）にする
  2. PG のレビュー（鈴木）は 10月だけにする
  3. IT（佐藤）を 10月から 11月へ動かす
  4. ほかの行の月と、各行の合計時間は変えない
- 右側の **操作回数**（タップ換算つき: タップ・ドラッグ = 1、select の変更・セル入力 = 2）と **課題の達成度**（4 項目の自動判定）で
  到達経路を客観的に見比べる。「保存されるデータ」を開くと各行の `workMonths` / `monthlyHours` がライブで見える。
- 「PC / スマホ 390px」で表示幅を切替。スマホ枠は下部タブ Dock を含み、保存ボタンが Dock の上に固定されることを確かめられる。
  ハブの下段は 4 ページのスマホ表示を横に並べた iframe（それぞれ操作できる）。
- 「＋」「+R」で担当者行・レビュー行を足す、作業期間を変える（期間外の月は自動で寄せる）も試せる。「リセット」で初期状態に戻る。

## 各案

| 案 | 操作 | 計測（操作回数 / タップ換算） | 向いている場面 | 弱点 |
|----|------|------|----------------|------|
| 現状 | 行ごとに 開始・終了 の 2 select。担当者行・レビュー行も独立した select | **6 / 12** | — | 月が開くまで見えない。手数が人数に比例。2ヶ月期間で跨げない。スマホで月が読めない |
| **案A 月チップのレール** `a-month-chips.html` | 行の上に期間内の月を並べる。**タップ = その月だけ**、**なぞる = 範囲**（Shift+クリック／Shift+←→ でも）。担当者行・レビュー行は工程に連動、鎖ボタンで個別化 | **4 / 4** | 大半が単一月＋一部が複数月、という普段の見積。スマホ | 期間が 7ヶ月を超えるとチップが狭い（横スクロール or 月省略が要る）。非連続月は表せない（現状も同じ） |
| 案B ミニガントのバー `b-mini-gantt.html` | 各行が 1 本のバー。本体ドラッグで移動（長さ維持）、両端のつまみで伸縮、空いている月をタップで広げる。連動は案A と同じ | **5 / 5** | 期間の長さを見比べたいとき。マウス | ドラッグ前提。単一月バーは狭く、つまみと本体の区別が付きにくい。タッチではつまみを掴む精度が要る（実装は `js/actual-timeline.js` の長押し・スワイプ衝突の前例あり） |
| 案C 工程×月マトリクス `c-hours-matrix.html` | 月を列にし、セルに月ごとの工数を直接入れる。値のある月が作業月。合計を変えると均等配分、セルを変えると手動配分 | **9 / 17** | 月別配分（monthlyHours）まで一度に決めたいとき | 月を動かすだけでも数値を打つ。IT の移動は「先に新しい月へ入れてから旧月を消す」順序が要る（逆順は月ゼロで弾かれる）。合計を崩しやすい。スマホは横スクロール＋数値キーボード |

計測は 2026-09-12 に Playwright で共通課題を最短手順で操作したときの値（PC・スマホ 390px タッチとも同じ手数）。

### 案A の操作モデル

- **タップ = この月だけ**。単一月の移動は 1 タップで終わる（課題①の解）。複数月のレールをタップしても「その月だけ」になる（予測可能性を優先）。
- **なぞる = 範囲**。pointerdown した月を起点に pointermove で範囲を塗り、pointerup で確定。`touch-action: pan-y` で縦スクロールは残す。
  Shift+クリック／Shift+←→ で既存範囲を伸ばす。Space/Enter でフォーカス中の月だけにする。
- 連続して選ばれた月は **1 本のピルに溶けて見える**（角丸を範囲の両端だけに付ける）。行間で列が揃うので、表全体でウォーターフォールが形として読める。
- 期間 2ヶ月でも 2 チップになるだけで跨げる（現状の単一 select 制約が消える）。
- 再描画は pointerup の外（`setTimeout 0`）で行う。pointerup の中で DOM を差し替えると、Chromium のタッチ操作で次のタップの click が合成されない
  （モックアップ検証で実測。本実装でも同じ注意が要る）。再描画時はモーダル本文の scrollTop を復元する。

### 3 案に共通する設計上の約束

- **担当者行・レビュー行は既定で工程行に連動**（鎖アイコン、`linked: true`）。連動中は工程の月の写し（淡い塗り・破線枠）で触れない。
  鎖を押すと現在の月を引き継いで個別設定になり、もう一度押すと工程に合わせ直す。「＋」「+R」で足した行も連動から始まる。
  → 現状の「同じ月を人数分選ぶ」手間が消え、レビューだけ最終月にする、という例外だけ触る。
- 月軸は既存の **作業期間（開始〜終了 select）** をそのまま使う。期間を縮めて外れた月は最寄りの端へ寄せ、その旨を通知する。
  「単一月／複数月」ラジオは廃止候補（開始 = 終了 なら月は 1 つになる）。
- 保存時の按分は既存の `splitHoursEvenly`（B-041① の未丸め保存を同時に解消）。モックアップは 0.25h 刻みで合計が崩れない按分で代替表示している。
- 保存データは現状と同じ `{ workMonth, workMonths: ['YYYY-MM', …], monthlyHours: { 'YYYY-MM': h } }`。B-021 のような `workMonth` だけの更新はしない。
- スマホ（≤768px）はモーダルを全画面にし、**保存／キャンセルを下部に固定**して本文だけをスクロールさせる。行は 2 段（1 段目: 工程・担当・時間・＋、2 段目: 作業月）。
  タッチ目標は 44px 以上。

## デザイン上の判断

- 新しく足した色は「選んだ月の塗り（`--accent`）」と「連動中の写し（`--accent-light` ＋ 破線）」の 2 つだけ。それ以外はすべて既存トークンで組んだ。
- 一点だけ目立たせる要素は **月レール**。ドロップダウンの中に隠れていた月を行の上に出し、連続月をピル 1 本に見せる。
  周りの select・input・btn・badge は本番の部品そのまま。
- 連動の状態は「鎖アイコン（実線＝連動／破線＝個別）」＋「レールの塗り（濃＝自分の値／淡＝写し）」の 2 つで冗長に示し、色だけに頼らない。
- 現状ページのスマホ表示だけは本番の列幅（工程 40px・時間 50px・作業月 100px・＋ 32px）を 1 行に保ち、B-046 の「月が読めない」を意図的に再現している。

## 推奨: 案A を土台にし、月別配分は案C の考え方を後付けする

1. 課題の 2 つ（単一月の手間・視覚的でない）を最少手数（4 操作）で解き、**ドラッグ無しでも全操作が終わる**のは案A だけ。
   案B は「長さが見える」が、案A でも連続月がピル 1 本に見えるので大半を吸収でき、タッチのつまみ精度という弱点を持ち込まない。
2. 案C が解く「月別配分」は今回の課題の外側。必要になったら案A の行に「配分…」（既存の単一見積編集モーダル `updateEditMonthPreview` と同じ 均等／手動）を
   足す方が、毎回の入力量を増やさずに済む。
3. 実装面: チップは `<button aria-pressed>` の並びで、pointer 3 イベント＋キーボードで完結する。案B のドラッグ計算・つまみのヒット領域・タッチ衝突より小さい。

段階分け（想定）:

1. 案A のレール（タップ／なぞる／Shift）＋ 担当者行・レビュー行の連動 ＋ スマホの 2 段レイアウトと固定フッター ＋ `splitHoursEvenly` 化 ＋ e2e
2. 期間 7ヶ月超のレール（横スクロール or 月省略）、「配分…」の後付け
